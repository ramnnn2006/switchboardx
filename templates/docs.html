Package publication is pending. The current local build plans in process; the requested HydraDB backend is being implemented and is not yet verified. The current benchmark measures seven fixture tasks, not a general latency guarantee.

terminal
1# After switchhboard-mcp is published on npm
2npx -y switchhboard-mcp stats

4# Get a local plan

Connect your agent

One stdio MCP server, once the switchhboard-mcp package is published. It exposes plan, report_run and catalog_stats. The current local build runs in process. HydraDB integration is in progress; these setup commands will be updated when its backend is tested. Schemas are included where available; missing schemas must be fetched from the actual MCP server.

terminal
1# Available after npm publication
2claude mcp add switchboard -- npx -y switchhboard-mcp
3claude mcp list

Run it in your project. Check it with claude mcp list.

Call the API directly

Send a task to get tool identities, typed inputs and call order. The current product measured 700 mean plan tokens against 110,238 preload-all tokens over seven fixture tasks. This is not a general performance guarantee.

HTTP API
1POST http://127.0.0.1:8787/api/plan
2{ "task": "Find open login bugs in Linear and post a summary to #eng",
3  "held": [{ "type": "slack.channel_id", "value": "C0123ENG" }] }

The plan contract

POST /api/plan accepts task, held, exclude and allow_destructive. Steps come in call order. Full input schemas are available for 51 of 420 starter tools; fetch missing schemas from the actual MCP server. The official ingested catalog has schemas for all 37 tools.

response · /api/plan
{
  "note": "Illustrative response shape. Actual fields and values depend on the task.",
  "plan_id": "pl_example",
  "steps": [
    {
      "order": 1,
      "tool_id": "server.tool",
      "consumes": [],
      "yields": [],
      "schema": "included only when present in the catalog"
    }
  ],
  "guard": {
    "status": "ok",
    "note": "Plan-time heuristics only, not runtime protection"
  }
}

Three more endpoints:

/api/plan_baseline
BM25 top-k over the same catalog, for comparison.
/api/report_run
Log what ran. Each report strengthens the NEXT edges between the tools you called.
/api/guard/check
Check the plan-time risk pattern. Pass held values to plan or report_run to retain known values.

Add your own servers

List your MCP servers, run the harvest, re-ingest. Parameters map onto a shared type vocabulary, so a GitHub repo and a GitLab repo stay different types. That's what makes the edges typed.

servers.json
1# Import a live server into a local catalog
2npx -y switchhboard-mcp ingest \
3  --server "npx -y @modelcontextprotocol/server-filesystem /absolute/allowed/path" \
4  --name filesystem --catalog ./catalog.json
5
6# Plan using that catalog
7npx -y switchhboard-mcp --catalog ./catalog.json plan --task "Read a file"

Risk flags and the guard

Every tool gets flags at ingest. If a plan holds all three trifecta legs, the edge into the sink is cut before your agent sees it. Watch it happen.

  • reads_private
    reads private data
  • ingests_untrusted
    ingests untrusted content
  • exfil_sink
    can exfiltrate
  • destructive
    destructive
Flags come from heuristics, so they can miss a risky tool. The guard checks plans. It does not sandbox the calls your agent makes.

Where it runs

The graph, the planner and the guard run from the repo on your machine. The hosted site can't reach a database, so it shows recorded plans and labels them replay.
