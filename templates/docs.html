Quickstart

HydraDB, the planner and this site all run on your machine. No API key. A plan comes back in 269 ms at p50 over 140 benchmark plans.

terminal
1# 1 · start HydraDB (node + indexer, all local)
2./start-hydradb.sh
3
4# 2 · load the catalog: 420 tools from 20 MCP servers
5npm run ingest
6
7# 3 · start the API on :8787
8npm run server
9
10# 4 · ask for a plan
11curl -s localhost:8787/api/plan \
12  -H 'content-type: application/json' \
13  -d '{"task":"Open a PR on acme/api fixing the flaky login test"}'

Connect your agent

One MCP server on stdio: npx -y switchhboard-mcp . Your agent gets a plan tool that returns the tools for a task, in call order. Needs HydraDB running locally, or set SB_API_URL to a running Switchboard API.

terminal
1claude mcp add switchboard \
2  -e HYDRA_BOLT_URL=bolt://127.0.0.1:7687 \
3  -- npx -y switchhboard-mcp

Run it in your project. Check it with claude mcp list.

Call the API directly

Your agent sends a task and gets back the tools it needs, in order, with their schemas. The average plan is 469 tokens, against 110,238 to preload all 420 tools.

HTTP API
1POST http://127.0.0.1:8787/api/plan
2{ "task": "Find open login bugs in Linear and post a summary to #eng",
3  "held": [{ "type": "slack.channel_id", "value": "C0123ENG" }] }

The plan contract

POST /api/plan takes { task, held?, exclude?, allow_destructive? } and returns this. Steps come in call order. explain.cypher is the exact query, so you can replay any plan in HydraDB.

response · /api/plan
1{
2  "plan_id": "pl_…",
3  "capabilities": ["code.open_pr"],
4  "held":  [{ "type": "github.repo", "value": "acme/api", "source": "mention:acme/api" }],
5  "steps": [
6    { "order": 1, "tool_id": "github.list_branches",       "role": "prerequisite",
7      "consumes": [{ "param": "owner+repo", "type": "github.repo", "from": "held" }],
8      "yields":   [{ "field": "$", "type": "github.branch" }], "schema": { … }, "schema_tokens": 120 },
9    { "order": 2, "tool_id": "github.create_pull_request", "role": "goal", … }
10  ],
11  "tokens": { "plan": 304, "preload_all": 110238, "saved": 109934 },
12  "guard":  { "status": "ok", "rejected": [] },
13  "explain": { "cypher": "CALL algo.MSpaths(…)", "ms": 269, "transport": "bolt" }
14}

Three more endpoints:

/api/plan_baseline
BM25 top-k over the same catalog, for comparison.
/api/report_run
Log what ran. Each report strengthens the NEXT edges between the tools you called.
/api/remember
Store a value you already have, like a repo, so plans skip the lookup.

Add your own servers

List your MCP servers, run the harvest, re-ingest. Parameters map onto a shared type vocabulary, so a GitHub repo and a GitLab repo stay different types. That's what makes the edges typed.

servers.json
1// ingest/servers.json: one entry per MCP server you want in the graph
2[
3  { "id": "github", "command": "npx", "args": ["-y", "@github/github-mcp-server"] },
4  { "id": "linear", "command": "npx", "args": ["-y", "linear-mcp"], "env": { "LINEAR_API_KEY": "dummy" } }
5]
6// harvest only calls tools/list, so dummy credentials are fine

Risk flags and the guard

Every tool gets flags at ingest. If a plan holds all three trifecta legs, the edge into the sink is cut before your agent sees it. Watch it happen.

  • reads_private
    reads private data
  • ingests_untrusted
    ingests untrusted content
  • exfil_sink
    can exfiltrate
  • destructive
    destructive
Flags come from heuristics, so they can miss a risky tool. The guard checks plans. It does not sandbox the calls your agent makes.

Where it runs

The graph, the planner and the guard run from the repo on your machine. The hosted site can't reach a database, so it shows recorded plans and labels them replay.
